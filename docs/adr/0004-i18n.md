# 0004 — Internationalisation

Status: accepted

## Context

Every user-facing string must be translatable (en default, pt-BR now), with the UI language following the browser unless the user chooses.

## Decision

- **i18next + react-i18next**, initialised synchronously from bundled resources (`src/i18n`), so there is no loading state and tests need no setup.
- `i18n/` is a low layer (imports nothing; `state`, `features` and `app` may import it; `ui` may not — primitives take strings through props).
- Core strings live in the `common` namespace (`locales/en.ts` is the source of truth; `locales/pt-BR.ts` is type-checked to have the same shape). Features own their strings: they call `registerTranslations(namespace, { en, 'pt-BR' })` and `useTranslation(namespace)`.
- The language preference is `system` (default) | `en` | `pt-BR`, in a versioned Zustand store (`state/locale.ts`). `app/providers/I18nProvider` applies it, resolves `system` with `detectLocale`, follows `languagechange`, and keeps `<html lang>` in sync. Language names are shown as endonyms.
- `i18n.test.ts` asserts every locale has the same keys and no empty strings.

## Consequences

- A new locale = one file in `locales/`, an entry in `LOCALES`/`LOCALE_NAMES`.
- Typed translation keys are not enforced globally (namespaces are registered at runtime); key parity is enforced by test instead.
